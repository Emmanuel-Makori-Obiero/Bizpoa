# Bizpoa project notes

Bizpoa is a bilingual English/Kiswahili prototype business manager using Africa's Talking USSD/SMS, a Vite website, Supabase Auth/Postgres, and a Node.js backend runtime.

Production storage uses the `bizpoa_*` relational tables created by `supabase/migrations/20261029_bizpoa_storage.sql`. RLS is enabled on every table, with no browser-role policies. The backend calls private `bizpoa_read_state` and `bizpoa_apply_state_delta` RPCs using `SUPABASE_SECRET_KEY` (or legacy `SUPABASE_SERVICE_ROLE_KEY`) kept only on the backend. The write RPC uses a global revision check and atomic transaction; the existing callback-based application logic is preserved over relational rows. The app currently loads a relational snapshot for each operation, which is suitable for this prototype but should be replaced with targeted indexed repository queries as volume grows.

The database stores businesses, transactions, SMS notes, language preferences, USSD sessions, owner OTP challenges, and OTP rate limits. The admin UI authenticates with Supabase Auth and `BIZPOA_ADMIN_EMAIL`; owner dashboards use the Bizpoa ID, registered phone, and SMS OTP. The connected project was initially empty and no local `data/bizpoa.json` was present, so no old records were imported.

USSD registration assigns a distinct `BZ-XXXXXX` Bizpoa ID and explains how to text Bizpoa at **62073** from the registered phone. USSD `0` backs up one step and `00` returns home. Management verifies ID plus caller phone before recording sales/expenses. Audits accept 1–365 days and offer SMS summary or a signed 24-hour CSV link when configured. The owner dashboard supports a selected date range, filtered ledger, CSV download, statement-by-SMS, stored owner notes, and Gemini summaries.

Incoming SMS now receives feedback: verified owners get an AI or fallback reply; unregistered/unlinked numbers get safe setup instructions and their message is not stored. An included Bizpoa ID must match the sending registered phone. Gemini can summarize a safe text message and draft a short reply; it cannot create or edit ledger transactions. Delivery still requires an Africa's Talking inbound callback plus backend SMS credentials. The browser voice-call demo uses ElevenLabs agent `agent_5301m63nex5rfxe9phm907ng2r57`; it is not connected to phone calls or business records.

Vercel deployment uses the root `vercel.json` configuration: Vite builds to `frontend/dist`, and `api/[...path].js` is the shared Node.js Function entry point for `/api/*`. Public `/health`, `/ussd`, `/sms/incoming`, and `/statement/*` paths rewrite to that function; the handler normalizes these aliases to the existing routes. `src/server.js` exports `handleRequest` and only starts a listening HTTP server when directly run locally. Vercel `waitUntil` keeps SMS processing and outgoing SMS work alive after webhook acknowledgements.

Local development uses `BIZPOA_STORAGE_DRIVER=json` from `.env.example`; production defaults to Supabase. Deployments must supply the Supabase server secret, `BIZPOA_ADMIN_EMAIL`, owner-session and statement-signing secrets, public URL, Africa's Talking credentials, and backend `GEMINI_API_KEY`. Set frontend public Supabase variables as build-time `VITE_*` settings; never expose the server-only database key.

The automated Vercel adapter tests and production frontend build pass. Running `vercel dev` or deploying still requires the user's authenticated Vercel account/project; this environment has no Vercel login. The SMS AI per-sender throttle remains process-local best-effort and should be made durable in Supabase before relying on it as a strict cross-instance limit.
